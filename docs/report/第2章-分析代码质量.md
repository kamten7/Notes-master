# 第 2 章 分析代码质量

## 2.1 人工阅读：优点

**优点一：文件夹计数交给 SQL 触发器，不靠调用方自觉。**

文件夹的 `notes_count` 是冗余字段，插入、删除、移动便签都可能让它失真。工程没有在 Java 里逐处加减，而是建了 8 个触发器在数据库层维护：

```java
// NotesDatabaseHelper.java:90
private static final String NOTE_INCREASE_FOLDER_COUNT_ON_UPDATE_TRIGGER =
    "CREATE TRIGGER increase_folder_count_on_update "+
    " AFTER UPDATE OF " + NoteColumns.PARENT_ID + " ON " + TABLE.NOTE +
    " BEGIN UPDATE " + TABLE.NOTE +
    "   SET " + NoteColumns.NOTES_COUNT + "=" + NoteColumns.NOTES_COUNT + " + 1" +
    "  WHERE " + NoteColumns.ID + "=new." + NoteColumns.PARENT_ID + "; END";
```

不管数据来自界面、备份导入还是同步模块，计数都不会漂。这比在每个调用点补一次 `updateCount()` 更省事，也让 `DataUtils` 里的移动逻辑可以写得很短。

**优点二：文案全部外置，升级按版本拆开。**

界面文字都在 `res/values/strings.xml`，另有 `values-zh-rCN`、`values-zh-rTW` 两套翻译。扫描 `src` 下所有 `.java`，中文字符串字面量为 0 处，说明没有把文案写死在代码里。

数据库升级没有写成一个大的 `if` 链，而是按版本分成 `upgradeToV2`、`upgradeToV3`、`upgradeToV5` 三个方法（`NotesDatabaseHelper.java:306` 起），每一步只做一件事，可以单独回看：

```java
// NotesDatabaseHelper.java:374
private void upgradeToV5(SQLiteDatabase db) {
    db.execSQL("ALTER TABLE " + TABLE.NOTE + " ADD COLUMN " + NoteColumns.IS_LOCKED
            + " INTEGER NOT NULL DEFAULT 0");
    db.execSQL("ALTER TABLE " + TABLE.NOTE + " ADD COLUMN " + NoteColumns.TAGS
            + " TEXT NOT NULL DEFAULT ''");
}
```

## 2.2 人工阅读：不足

**不足一：工具层反向依赖表现层，包之间成环。**

```java
// DataUtils.java:32
import net.micode.notes.ui.NotesListAdapter.AppWidgetAttribute;
```

`tool` 本该是最底层，现在为了读桌面小部件的属性，反过来引用了 `ui` 里的内部类。后果有两个：工具层没法脱离界面单独复用或测试；包图 1-1 里 `tool` 和 `ui` 之间出现双向箭头，依赖成环。要改的话，把 `AppWidgetAttribute` 挪到 `model` 或 `tool` 即可，`NotesListAdapter` 改成引用新位置。

**不足二：批量操作没有事务，出错了会留下半截数据。**

`DataUtils` 的批量移动先攒操作再提交：

```java
// DataUtils.java:113
ContentProviderResult[] results = resolver.applyBatch(Notes.AUTHORITY, operationList);
```

看起来是原子操作，实际上 `NotesProvider` 没有重写 `applyBatch`，用的是 ContentProvider 的默认实现——逐条 `apply()`，不包事务。移动 10 条便签，第 6 条失败时前 5 条已经落库，后 4 条没动，用户看到的就是"移了一半"。正确做法是在 Provider 里重写 `applyBatch`，用 `beginTransaction()` 包住整个循环，失败回滚。

**不足三：超长方法与职责混杂。**

```java
// SqlNote.java:229
public boolean setContent(JSONObject js) {   // 132 行
```

全工程最长的方法。它同时干四件事：解析服务端 JSON、区分 system / folder / note 三种类型、写本地字段、处理异常。分支多到没法逐条测，改一处要重读整个方法，异常还被 `catch` 后只打了一句日志，调用方分不清是解析失败还是字段缺失。按类型拆成三个方法、让 `setContent` 只做分派，会好很多。

另外两处小问题：同步链路还在用 `AsyncTask`（`GTaskASyncTask`、`NotesListActivity`），这个类从 Android 11 起已废弃；源码里还有 13 处 `TODO`，其中 `NotesProvider#getType` 直接 `return null`，接口没实现完。

## 2.4 典型问题

表 2-2 典型问题记录

| 序号 | 位置 | 问题 | 原因 | 改进 |

第 1 条要单独说一句：它不是原工程的问题，是本次适应性维护带进来的。原代码调用的 `setLatestEventInfo` 在新 SDK 里被删了，不换就编译不过；换成 `Notification.Builder` 后 `build()` 要求 API 16，而工程最低支持 14，低版本设备走到这个分支会崩。这条在第 4 章 4.4 里作为遗留问题记着，没有藏。
